---
title: "Run a scenario"
description: "Run your agent against multiple inputs and assert on every result."
---

A [scenario](/concepts/scenarios) is a named set of test cases for your agent. Each run posts pass/fail results to the dashboard so you can track quality over time.

Scenarios have two item types:

| Type | How it works | Cost |
|------|-------------|------|
| **Synthetic** | Live LLM, fresh input you define | Real API cost |
| **Trace-backed** | Replays a recorded production trace: live model, recorded tool data | Model calls only |

## RunScenarioAsync

<CodeGroup>
```csharp C#
var result = await veval.RunScenarioAsync(
    scenarioName:       "my-scenario",
    agent:              service.ExecuteAsync,
    scenarioAssertions: [
        TraceAssert.NoErrors(),
        TraceAssert.MaxCost(0.10m),
        TraceAssert.StepExists("classify"),
    ],
    items: [
        new ScenarioItem { Name = "question 1", Input = "What is prompt caching?" },
        new ScenarioItem { Name = "question 2", Input = "What is tool use?" },
    ]
);
```

```python Python
result = await veval.run_scenario_async(
    scenario_name="my-scenario",
    agent=service.execute_async,
    scenario_assertions=[
        TraceAssert.no_errors(),
        TraceAssert.max_cost(0.10),
        TraceAssert.step_exists("classify"),
    ],
    items=[
        ScenarioItem(name="question 1", input="What is prompt caching?"),
        ScenarioItem(name="question 2", input="What is tool use?"),
    ],
)
```

```javascript Node
const result = await veval.runScenarioAsync(
  "my-scenario",
  (ctx) => service.execute(ctx),
  [
    TraceAssert.noErrors(),
    TraceAssert.maxCost(0.10),
    TraceAssert.stepExists("classify"),
  ],
  [
    { name: "question 1", input: "What is prompt caching?", assertions: [] },
    { name: "question 2", input: "What is tool use?", assertions: [] },
  ]
);
```
</CodeGroup>

| Parameter | Description |
|-----------|-------------|
| `scenarioName` | Identifies the scenario in the dashboard |
| `agent` | Your agent — same signature as `RunAsync` |
| `scenarioAssertions` | Assertions that apply to every item |
| `items` | List of `ScenarioItem` — inline or fetched from dashboard |

## Synthetic items

Use these for new inputs you want to test with a live LLM.

<CodeGroup>
```csharp C#
new ScenarioItem
{
    Name  = "prompt caching question",
    Input = "Explain prompt caching in one sentence.",
}
```

```python Python
ScenarioItem(
    name="prompt caching question",
    input="Explain prompt caching in one sentence.",
)
```

```javascript Node
{ name: "prompt caching question", input: "Explain prompt caching in one sentence.", assertions: [] }
```
</CodeGroup>

## Trace-backed items

Use these to turn a recorded production trace into a regression test. Steps recorded as `llm` run live with your current prompt, so a prompt change that makes the output worse fails the item. Every other step (tools, untyped steps) returns its recorded output, so the replay sees the same data as the original run and never reaches a real system.

Mark your model steps when you record the trace, and your tools with `"tool"`. For model steps, give the type where the step is called, so a replay that reaches a model step the recording never contained can still run it live:

<CodeGroup>
```csharp C#
var fields = await ctx.TrackStepAsync("extraction", page, step => ExtractAsync(page, step),
    new StepOptions { Type = StepType.Llm });
```

```python Python
fields = await ctx.track_step_async("extraction", page, extract, StepOptions(type=StepType.LLM))
```

```javascript Node
const fields = await ctx.trackStepAsync("extraction", page, (step) => extract(page, step), { type: StepType.Llm });
```
</CodeGroup>

`step.SetMeta("type", "llm")` (`set_meta` / `setMeta`) inside the step also works for steps the recording has. If no step of a trace-backed item ran live, the item fails and tells you to mark the model steps.

<CodeGroup>
```csharp C#
new ScenarioItem
{
    Name    = "production trace replay",
    TraceId = "tr_4ec4e79c5d03...",
    Assertions = [TraceAssert.MaxCost(0.05m)],  // per-item assertion
}
```

```python Python
ScenarioItem(
    name="production trace replay",
    trace_id="tr_4ec4e79c5d03...",
    assertions=[TraceAssert.max_cost(0.05)],  # per-item assertion
)
```

```javascript Node
{
  name: "production trace replay",
  trace_id: "tr_4ec4e79c5d03...",
  assertions: [TraceAssert.maxCost(0.05)],  // per-item assertion
}
```
</CodeGroup>

<Note>
  The trace must have recorded steps. If it has none, Veval throws rather than silently calling the live LLM.
</Note>

### Mocked trace-backed items

Set `MockModelSteps` to serve model steps from the recording too. The item is then free and deterministic, which suits checking a code change (routing, parsing, tool wiring), but it can't catch a prompt regression: every model call returns what the old prompt produced.

<CodeGroup>
```csharp C#
new ScenarioItem { TraceId = "tr_4ec4e79c5d03...", MockModelSteps = true }
```

```python Python
ScenarioItem(trace_id="tr_4ec4e79c5d03...", mock_model_steps=True)
```

```javascript Node
{ trace_id: "tr_4ec4e79c5d03...", mock_model_steps: true, assertions: [] }
```
</CodeGroup>

To mock every trace-backed item in a run, including items loaded from the dashboard, pass the option to `RunScenarioAsync` in `ScenarioOptions`:

<CodeGroup>
```csharp C#
await veval.RunScenarioAsync("my-scenario", agent, assertions, options: new ScenarioOptions { MockModelSteps = true });
```

```python Python
await veval.run_scenario_async("my-scenario", agent, assertions, options=ScenarioOptions(mock_model_steps=True))
```

```javascript Node
await veval.runScenarioAsync("my-scenario", agent, assertions, undefined, { mock_model_steps: true });
```
</CodeGroup>

`VevalTestSdk` always replays trace-backed items mocked, so a test built on it never makes a live model call.

### Keeping the trace

Traces are deleted after your plan's retention window. Each time a scenario replays a trace, its retention restarts, so a trace your tests replay at least once per window stays.

To keep a trace no matter how often it runs, open it in the dashboard and click **Use as fixture**. This pins the trace and shows the `ScenarioItem` for it in each language, ready to copy. **Pin** on its own keeps the trace without showing the item. Each plan allows a set number of pinned traces (25 on Free); unpin one to free a slot.

If the trace is gone, the item fails with `trace '<id>' not found` and the scenario's other items still run.

## Per-item assertions

Each `ScenarioItem` can carry its own assertions on top of the scenario-level ones:

<CodeGroup>
```csharp C#
new ScenarioItem
{
    Name       = "expensive question",
    Input      = "Write me a novel.",
    Assertions = [TraceAssert.MaxCost(0.50m)],  // only for this item
}
```

```python Python
ScenarioItem(
    name="expensive question",
    input="Write me a novel.",
    assertions=[TraceAssert.max_cost(0.50)],  # only for this item
)
```

```javascript Node
{
  name: "expensive question",
  input: "Write me a novel.",
  assertions: [TraceAssert.maxCost(0.50)],  // only for this item
}
```
</CodeGroup>

## Fetching items from the dashboard

If `items` is `null`, Veval fetches items for the scenario from the API automatically. This lets you manage test cases in the dashboard without redeploying code.

<CodeGroup>
```csharp C#
// items: null → fetched from dashboard by scenarioName
var result = await veval.RunScenarioAsync(
    scenarioName:       "my-scenario",
    agent:              service.ExecuteAsync,
    scenarioAssertions: [TraceAssert.NoErrors()]
);
```

```python Python
# items=None → fetched from dashboard by scenario_name
result = await veval.run_scenario_async(
    scenario_name="my-scenario",
    agent=service.execute_async,
    scenario_assertions=[TraceAssert.no_errors()],
)
```

```javascript Node
// items omitted → fetched from dashboard by scenarioName
const result = await veval.runScenarioAsync(
  "my-scenario",
  (ctx) => service.execute(ctx),
  [TraceAssert.noErrors()]
);
```
</CodeGroup>

## ScenarioRunResult

<CodeGroup>
```csharp C#
Console.WriteLine(result.Summary);
// failed — 5 passed, 1 failed, 2 inconclusive (25% of replays > 0% allowed), 6/8 replays stayed on path

foreach (var item in result.Results)
{
    Console.WriteLine($"{item.Item.Name}: {item.Summary}");
    foreach (var failure in item.Failures)
        Console.WriteLine($"  → {failure}");
}
```

```python Python
print(result.summary)
# failed — 5 passed, 1 failed, 2 inconclusive (25% of replays > 0% allowed), 6/8 replays stayed on path

for item in result.results:
    print(f"{item.item.name}: {item.summary}")
    for failure in item.failures:
        print(f"  → {failure}")
```

```javascript Node
console.log(result.summary);
// failed — 5 passed, 1 failed, 2 inconclusive (25% of replays > 0% allowed), 6/8 replays stayed on path

for (const item of result.results) {
  console.log(`${item.item.name}: ${item.summary}`);
  for (const failure of item.failures)
    console.log(`  → ${failure}`);
}
```
</CodeGroup>

An item's summary says how it ended and, for a replayed item, how much of its recording it used, e.g. `passed — 40/64 recorded steps used, 3 diverged but served, 12 live, stayed on path` or `inconclusive at step 7 'fill' — 6/64 recorded steps used, 0 diverged but served, 3 live, left the path`. A live replay may legitimately take a shorter path than the recording, so unused recorded steps don't fail it.

| Member | Description |
|--------|-------------|
| `Passed` | True if no item failed and the share of replayed items that were inconclusive is within `MaxInconclusiveRate` |
| `PassCount` | Number of passing items |
| `FailCount` | Number of failing items; inconclusive items aren't counted here |
| `InconclusiveCount` | Number of items whose live replay left its recording and stopped |
| `InconclusiveRate` | `InconclusiveCount` as a share of replayed items, 0 to 1; synthetic items can't be inconclusive, so they don't count |
| `StayedOnPathRate` | Replayed items that stayed on their recorded path, as a share of replayed items; null when nothing was replayed |
| `Summary` | The run in one line |
| `Results` | List of `ItemRunResult`, each with `Outcome`, `Failures`, `Inconclusive` and `Summary` |

Python and Node use snake_case: `pass_count`, `inconclusive_count`, `stayed_on_path_rate`, and so on.

`RunScenarioAsync` doesn't throw when items fail, so assert on `Passed` in your test, with the summary as the message. A failing CI run then says why in one line instead of a bare `false`:

<CodeGroup>
```csharp C#
Assert.True(result.Passed, result.Summary);
```

```python Python
assert result.passed, result.summary
```

```javascript Node
assert.ok(result.passed, result.summary);
```
</CodeGroup>

### Inconclusive items

A trace-backed item whose live replay asks for a step the recording doesn't have stops there and is **inconclusive**: nobody knows what the real tool would have returned, so it neither passes nor fails (see [when the run leaves the recording](/concepts/replay#when-the-run-leaves-the-recording)). Its `Inconclusive` (`inconclusive`) holds the step where it left the path and both inputs, and the dashboard shows it with an *inconclusive at step N* badge.

By default, any inconclusive item fails the run: a prompt change that sends every item off its recorded path must not look green in CI. If some items needing a real run is acceptable, raise `MaxInconclusiveRate` (`max_inconclusive_rate`), the largest share of replayed items that may be inconclusive in a passing run. A failed item fails the run whatever the threshold. When the threshold alone fails a run, its summary starts with `failed: too many inconclusive`.

<CodeGroup>
```csharp C#
// Pass with up to one item in ten inconclusive.
var result = await veval.RunScenarioAsync("my-scenario", agent, assertions,
    options: new ScenarioOptions { MaxInconclusiveRate = 0.1 });
```

```python Python
# Pass with up to one item in ten inconclusive.
result = await veval.run_scenario_async("my-scenario", agent, assertions,
                                        options=ScenarioOptions(max_inconclusive_rate=0.1))
```

```javascript Node
// Pass with up to one item in ten inconclusive.
const result = await veval.runScenarioAsync("my-scenario", agent, assertions, undefined, { max_inconclusive_rate: 0.1 });
```
</CodeGroup>

Don't map an inconclusive item to a skipped test: CI ignores skips. `StayedOnPathRate` (`stayed_on_path_rate`) tells you how far live replay can be trusted for the change under test; the dashboard shows it for each run.

### Faults in scenarios

`ScenarioOptions.Faults` and `ScenarioItem.Faults` inject failures into trace-backed items, to test retries and fallbacks across many recordings at once. An item that stops after a fault is counted in `InconclusiveAfterFaultCount` (`inconclusive_after_fault_count`) and always fails the run, whatever `MaxInconclusiveRate` allows. See [Test failure paths](/guides/failure-paths#in-scenarios).
