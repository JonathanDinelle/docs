Replay runs your real agent code, but each step returns the output recorded in a [trace](/concepts/traces) instead of calling the LLM. Tests built on replay are deterministic, fast, and free.

## How replay fits in

`VevalTestSdk` is a test double for `IVevalSdk`. Load a trace with `WithReplay`, inject the test SDK into your agent in place of the real one, and call it normally. When your agent calls `TrackStepAsync`, the test SDK returns the output recorded for that call.

Have your agent accept the `IVevalSdk` interface, not the concrete class, so your tests can swap in `VevalTestSdk`.

Replay also powers trace-backed [scenario](/concepts/scenarios) items.

## Strict mocking

`VevalTestSdk` never falls through to the live LLM. If your agent calls `TrackStepAsync` with a step name that isn't in the recorded trace, it throws:

```text
InvalidOperationException: Replay mode: no mock output for step 'new_step'.
Available steps: classify, answer.
This would have made a real LLM call.
```

A code change that adds a new LLM call fails the test instead of quietly making real calls.

## How calls are matched to the recording

Each `TrackStepAsync` call is served a recorded step with the same name. When several recorded steps share that name, replay picks the one whose input is identical to the call's input (key order doesn't matter), so calls that changed order still get their own outputs. If none is identical, replay uses the next unused recording of that step in recorded order and marks the call **diverged**.

In mocked mode, a replay fails if your agent:

* calls a step more times than the trace recorded (the strict error above), or
* never calls a step the trace recorded. A skipped branch would otherwise leave your assertions passing on a path the recording doesn't cover.

A diverged input doesn't fail the replay on its own: prompts often contain dates or IDs that change on every run. Each replay result reports how every call was matched in `Fidelity` (`fidelity` in Python and Node): which calls matched, which diverged with the recorded and actual input side by side, and which recorded steps went unused.

## Guarding against drift

To also fail when inputs drift, turn on `CompareWithRecording` in `ReplayOptions`. The replay then fails when its step sequence or any step input differs from the trace it's replaying. List fields that legitimately change on every run in its `IgnoreFields`; Veval never ignores a field you didn't list.

Mocked replay checks control flow and code changes. It can't tell you whether a new prompt is better, because every model call returns what the old prompt produced. To test a prompt change, replay live.

## Live replay

With `LiveModelSteps` in `ReplayOptions`, steps recorded as `llm` run for real and every other step is served from the recording. A prompt change shows up in the output, while tool calls (a portal visit, a payment) return what they returned in production and never reach a real system. Trace-backed [scenario](/concepts/scenarios) items replay this way by default.

* A step recorded as `tool` or left untyped is served from the recording, never run.
* A model step called more often than recorded runs live too.
* A call to a step the trace never recorded fails the replay, because Veval can't tell whether running it is safe.
* A recorded step the agent didn't call is reported in `Fidelity` but doesn't fail the replay: a live model can take a different path.
* If no step ran live, the replay fails, because nothing could have caught a prompt change. Mark model steps with `SetMeta("type", "llm")` when you record.

## Reporting

`VevalTestSdk` still reports traces and scenario results to the dashboard, so replay runs count in your history.
